Modeling Clinic Strategy with Claude: What I Learned

The idea

After finishing the Open Payments dashboard, I turned to a question closer to home. Our pediatric gastroenterology division had just adopted a new practice plan, which changes how physician effort and clinic time translate into departmental finances. Leadership needed to think through how we structure our two clinic types — general GI visits, and a specialty clinic (motility) that runs longer, more complex follow-up visits — and I wanted real numbers to think with, not gut feel.

Unlike the payments project, there was no public dataset to wrangle. The raw material here was Medicare's own billing rules: every office visit code has an assigned "work RVU" (a standardized unit of physician effort) and, since our clinic bills by time, a required number of minutes to bill at each complexity level. I wanted to turn those rules into an actual model of our clinic template.

Phase 1: A spreadsheet first

Same instinct as last time — start with something disposable. I built a spreadsheet using the real CMS work-RVU values and time thresholds for office visit codes, modeling exactly how much production a clinic session could generate given our slot lengths. I deliberately used a placeholder assumption at first (a 50/50 split between two common billing levels) just to get the structure right before worrying about whether the numbers were realistic.

Phase 2: Replacing guesses with real data

Once the spreadsheet worked, I went back and rebuilt the input side so it could accept our actual distribution across all five visit-complexity levels, once that billing data was available, instead of a stand-in split. Small change, but it's the difference between a demo and a tool someone could actually use to make a decision.

Phase 3: Accounting for no-shows

A slot on the calendar isn't the same as a completed, billable visit. I added our historical no-show rate to the model, applied separately to new and follow-up visits, since those rarely behave the same way.

Phase 4: From spreadsheet to something leadership could touch

A spreadsheet meant I was the bottleneck — every "what if we tried it this way" question meant re-opening the file myself. I turned it into an interactive web tool with Claude Code so department leadership could adjust the assumptions themselves and watch the numbers respond in real time.

Phase 5: Generalizing "motility" into "specialty"

The tool originally hard-coded our two clinic types by name. I generalized the second one into an editable "specialty clinic" concept — same structure, but the label, slot length, and every assumption underneath it can be changed, since other departments facing the same question won't call it motility.

Phase 6: Making results shareable without the live tool

Not everyone who needs to see a result should have to open the app. I added a one-click Excel export (a clean snapshot of the current inputs and outputs) and a print-to-PDF summary view, so the numbers could go into a meeting or an email on their own.

Phase 7: Solving "where does this live" without a server

I wanted people to be able to save and share a specific set of assumptions — but I didn't want to build a backend, and I especially didn't want one user's inputs visible to another. The answer was to encode the entire input state directly into the page's URL. Open a link, and your exact assumptions are right there. Nothing is stored anywhere, no login, and because of how the browser handles URLs, that data never even reaches a server — it only ever exists on the screen in front of you.

Phase 8: Going live

Once the model itself was solid, I handed the project to Claude Code for the parts I'd never done before — initializing git, pushing to GitHub, and setting up deployment. Along the way, while adding a new export feature, I introduced a small bug: a handful of dashes and arrows showed up as raw text (literally \u2014 instead of the character itself) in one export view. Caught it before calling anything finished — a good reminder that "it runs" and "it's correct" aren't the same test.

What I'd tell someone starting out

The most useful thing this project did wasn't the software — it was forcing precision. Describing our clinic's visits as "usually a level 3 or 4" feels specific enough in conversation, but building that into an actual calculation exposed something nobody had flagged before: our shorter clinic template doesn't contain enough scheduled time to bill some of the higher-complexity visits it's assumed to produce. That's a real operational finding, and it only became visible because the vague version got turned into a number.

I'd also say: let the tool show the tension instead of resolving it. This model can tell you, honestly, that one clinic type produces more revenue per hour than the other. It should not quietly talk anyone into cutting the one that scores lower — access to specialty care is part of the job, not a rounding error. A good model makes trade-offs visible; it doesn't make the decision for you.

Keep going down the rabbit hole. This one started as a spreadsheet question and ended up teaching me something true about how our clinic actually runs.
